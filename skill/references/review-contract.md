# 审稿契约与结论处理

## 一、什么时候送审

- 版本已 `seal`（哈希冻结），产物齐、`RUNLOG.md` 有、图已导出。
- 主 agent 自己已过一遍 `acceptance-checklist.md`。
- **不要**在代码还没跑通、图还是占位符的时候送审——那是浪费一次独立审稿。

## 二、审稿任务里放什么 / 不放什么

**放**：
- 版本目录绝对路径
- 产物清单（这次审哪些表、哪些图、哪些脚本）
- 研究问题与设计的一句话（让审稿人知道该用什么标准）
- 方案文件的路径（`plan.md`）
- 必须实际打开图表的要求

**不放**：
- 执行者的自述、主 agent 的解读、上一轮审稿意见（除非是复审，见第四节）
- "我觉得这个结果挺稳的"这类暗示

独立性是审稿价值的全部来源。给了暗示，审稿就退化成盖章。

## 三、四档结论与处理

| 结论 | 主 agent 的动作 | 是否升版本 | 是否需要用户介入 |
|---|---|---|---|
| `ACCEPT` | `epi_run.py verdict --verdict ACCEPT` → `deliver` → 向用户交付 | 否 | 否 |
| `MINOR` | 逐条修 → `next` 升版本 → 重跑受影响产物 → 重审 | 是 | 修完直接交付；若选择带 waiver 交付，**必须先问用户** |
| `MAJOR` | 回到"分析/计划"重做受影响部分 → `next` 升版本 → 重派 → 重审 | 是 | 若根因涉及研究设计或数据缺陷，先告知用户 |
| `REJECT` | 停止推进，向用户说明：设计/数据为什么不支持、可选的三条出路 | — | 必须 |

**硬规则**：
- `deliver` 只放行 `ACCEPT`（`MINOR` 需显式 `--waiver`，且 waiver 文本会写进 HISTORY）。
- 有任一 `major` 时，不得自行把结论降级为"小问题先交付"。
- `unverifiable` 非空 = 不能 ACCEPT。先补文件或补说明，再审。

## 四、复审

- 复审必须是**新的一次 agent 调用**（全新上下文），不能延续上一轮审稿人的会话。
- 复审任务里附上"上一轮 major 清单 + 本轮改动说明"，让审稿人逐条核销：
  `M1 已修 / 未修 / 部分修（说明）`。
- 只核销 major；minor 不必逐条回。

## 五、把审稿意见翻译成下一轮方案

审稿意见不是任务清单，不能直接粘贴给执行者。主 agent 要：

1. 判断每个 major 是**实现错**（重派执行者改代码）还是**设计错**（改方案、可能改模型设定）。
2. 实现错 → 直接进下一轮派发单，指名修 `M1`。
3. 设计错 → 先改 `plan.md`，可能连带重跑多个产物；在 `next --note` 里写明改了什么。
4. minor → 攒起来，在最后一轮一起做，不要为一条标签升一次版本。

## 六、结论记录

```bash
python scripts/epi_run.py verdict --dir <项目> --version v003 \
  --verdict MAJOR --reviewer <项目>/v003/review/review.json \
  --summary "未调整事件时间，暴露定义与方案不符"
```

`verdict` 会把结论写进 `v003/meta.json` 并重写 `HISTORY.md`。`deliver` 之前必须已有 verdict。
